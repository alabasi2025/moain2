# ADR-0011: تعديلات سلامة إضافية على المخطط (Integrity Amendments)

**الحالة:** مقترح — بانتظار موافقة صاحب المشروع · **التاريخ:** 2026-10-03
**الدليل:** `docs/07-implementation/evidence/verify_schema_findings.py` (الثغرات) و`verify_proposed_fixes.py` (الحل: 13/13)

## السياق
عند تنفيذ `04-schema.sql` كما هو وتجربته، نجح السيناريو الإلزامي (30 / 18,000) ونجحت immutability الدفتر. لكن ظهرت ثغرات تكسر "الثوابت العشرة":

| # | الثغرة المُثبتة | الثابت المكسور |
|---|---|---|
| S1 | ترحيل بأثر رجعي (F19 يسمح): `v_stock_on_hand` = 150 بينما `stock_balances` = 130 | F2، F20 |
| S2 | `occurred_at` بصيغة تاريخ فقط يجعل الترتيب النصي خاطئاً: العرض اختار 100 والصحيح 110 | F2 |
| S3 | D1 بلا `BEGIN`: قراءة ← حساب ← كتابة غير ذري بين طلبين متزامنين | F8، F9 |
| S4 | `posted ← draft` مقبول، ثم أسطر السند قابلة للتعديل | F7 |
| S5 | `committed ← open` مقبول في الجرد، ثم العدّ قابل للتعديل | G6 |
| S6 | `UPDATE delivery_lines` و`DELETE deliveries` مقبولان | E5 |
| S7 | الدور العام (`location_id NULL`) يتكرر | RBAC |
| S8 | سعر التقييم الصحيح × الكمية يُضيّع قيمة (603 مقابل 653) | J4 |
| S9 | إلغاء الطلبية يحجز (فرع، نافذة، يوم) للأبد | C1/C13 |
| S10 | 16 جدولاً ابناً بلا `tenant_id` | A1 كما صيغت |

## القرار (مقترح)
**المخطط الأصلي يبقى كما هو حرفياً** (`0000_baseline.sql`)، وتُضاف migration `0001_integrity.sql` **إضافية فقط**:

1. **صيغة `occurred_at`:** Trigger يفرض `YYYY-MM-DDTHH:MM:SS.sssZ`.
2. **سلسلة الدفتر:** Trigger `BEFORE INSERT` يرفض الحركة إن كان تاريخها أقدم من آخر حركة (`LEDGER_BACKDATED`)، أو إن لم يتحقق `qty_after = prev_qty + qty` (`LEDGER_CHAIN_BROKEN`)، أو إن لم يتحقق `value_after = prev_value + diff`. يحل S1 وS3 (القراءة القديمة تفشل ذرياً داخل `batch` ← إعادة محاولة واحدة).
3. **حالات نهائية:** Triggers تمنع `posted ← draft`، و`cancelled ← *` في السندات، وحذف سند غير مسودة، و`committed/cancelled ← *` في الجرد.
4. **التسليم:** منع DELETE على `deliveries`، ومنع UPDATE/DELETE على `delivery_lines`.
5. **`user_roles`:** `UNIQUE INDEX (user_id, role, COALESCE(location_id,''))`.
6. **`order_exceptions`:** `ADD COLUMN consumed_at TEXT`، و`ADD COLUMN edit_until TEXT` (لـ C7 و"لديك 15 دقيقة").
7. **التقييم (بلا تغيير مخطط):** `stock_value_minor_after` هو الحقيقة. الصادر = `round(q × value / qty)`، وآخر وحدة تأخذ القيمة المتبقية. `valuation_rate_minor_after = round(value / qty)` للعرض. **السيناريو الإلزامي يعطي النتيجة نفسها.**
8. **F19 يصبح:** رفض الحركة المؤرخة قبل آخر حركة للمادة/الموقع، برسالة عربية: «لا يمكن الترحيل بتاريخ أقدم من آخر حركة للمادة (3/10). استخدم تاريخ اليوم.»
9. **S9:** حدث جديد في آلة حالة الطلبية `reopen: cancelled ← submitted`، مسموح فقط إن ألغاها الفرع قبل الإغلاق، على **نفس الصف** مع `revision++`.
10. **S10:** يبقى المخطط. القاعدة تُنفَّذ هكذا: الجداول الأبناء لا تُلمس إلا عبر Repository جذرها المقيّد بـ `tenant_id`، مع فحص CI ساكن.

## البدائل المرفوضة
- **تعديل `04-schema.sql` نفسه:** يكسر "استخدمه كما هو". الـ migration الإضافية تُبقي الأصل مرجعاً وتجعل الفرق مقروءاً.
- **إعادة حساب الدفتر بعد كل ترحيل رجعي (نمط ERPNext repost):** يحتاج تعديل حركات سابقة، وهذا ممنوع بـ F1. التكلفة والتعقيد عاليان.
- **فهرس فريد جزئي لـ S9:** SQLite لا يغيّر UNIQUE بلا إعادة بناء الجدول. `reopen` أبسط ولا يمس المخطط.
- **الاكتفاء بفحص الخدمة (SVC):** الوثائق نفسها تضع هذه الثوابت في مستوى **DB** ("لا يمكن تجاوزها حتى من الأدمن").

## العواقب
- (+) كل ثابت "لا يُفاوَض" يصبح مفروضاً في DB فعلاً، ومُثبتاً باختبار.
- (+) لا تغيير على أي جدول أو View أصلي.
- (−) أمين المخزن لا يستطيع ترحيل فاتورة الأمس بعد تسجيل حركة اليوم على المادة نفسها. التخفيف: الواجهة تقترح تاريخ اليوم، والسند يحمل `external_ref` وتاريخ الفاتورة في `note`/`custom_fields`.
- (−) Trigger السلسلة يضيف قراءتين لكل حركة — مهمل بحجم المخابز (~50 حركة/يوم).
